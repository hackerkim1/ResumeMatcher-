## 1. 起点：为什么做这个项目

**背景**：刚学完 LangChain 的调用链（`prompt | llm | parser`），之前做过一个知识库问答（RAG）小项目，想再做一个项目巩固。

**选题过程**：先列了几个候选（信息抽取器、多意图路由、长文档总结、升级原项目、工具调用 Agent），又问“有没有实际实用价值的”，最后选了**简历 × 岗位匹配分析器**：输入简历和岗位描述，输出匹配分数、技能缺口、修改建议和面试题。

**一个值得记下来的追问**：“这些用 AI 也能做吧，为什么要做这种项目？”

答案是：做项目的价值不在“做出一个比 ChatGPT 更好的产品”，而在于学会**怎么让大模型可靠地干活**：检索回来的内容不相关怎么办、模型编造怎么发现、输出格式不对怎么兜底、成本和速度怎么控制。这些只有亲手做、亲手踩坑才会懂。选项目的标准也因此变成：**选“有固定流程、要批量、要集成”的任务，别选“聊天式的通用能力”**。

**开发方式**：按真实开发流程，**先搭框架，再逐步填充，每步可验证**；每个功能都按**测试驱动**（先写会失败的测试，看它变红，再写实现，变绿）。

## 2. 最终的框架

### 2.1 两条主流程

**单岗位匹配 `match`**（没有检索）：

```
简历文本 ──► 简历抽取链 ──► ResumeInfo ─────────────┐
                                                     ├──► 代码算分 ──► 报告
岗位描述 ──► 岗位抽取链(带缓存) ──► JobRequirement ──┤
                                                     │
简历原文 + 岗位技能清单 ──► 逐项判断链 ──► 对齐 ──► 依据核对 ──┘
```

**岗位库推荐 `recommend`**（向量检索 + 大模型判断）：

```
简历 ──► 抽取一次 ──► 拼成“技能+项目”查询文本
                          │
                          ▼
              Chroma 向量检索（bge-m3）──► 前 k 个候选岗位
                          │
                          ▼
         对每个候选岗位：抽取 → 逐项判断 → 对齐 → 核对 → 代码算分
                          │
                          ▼
                 按【总分】排序（不是按检索距离）
```

### 2.2 一条贯穿全项目的原则：**模型负责理解，代码负责计算**

| 谁做 | 做什么 |
|---|---|
| 大模型 | 把简历、岗位描述抽成结构化数据；逐项判断“简历是否体现了这项技能”并摘抄依据；写修改建议和面试题 |
| 代码 | 技能清单对齐、依据核对、总分计算、学历和学校检查、岗位库同步、排序 |

原因：模型做算术和精确匹配不可靠、结果有波动；代码结果确定、可测试、可解释。

## 4. 开发时间线

### 第 0 阶段：规划与分层

先想清楚模块各管什么，再动手。核心决定：

- 按**职责**分层，不按“我先写哪个”；
- `scoring.py` 不依赖模型 → 最容易测试 → **最先写**；
- `config.py` 是唯一读环境变量的地方；
- `.env.example`（模板）和 `.env`（真 key，被忽略）分开，`.gitignore` 先写好。

### 第 1 步：项目骨架（提交 `49a25bc` 的一部分）

建目录、空模块（只写职责说明）、`requirements.txt`、`.gitignore`、README、`git init`。

### 第 2 步：数据结构 + 评分（测试驱动）

**先写测试，我手算了答案**：

| 场景 | 手算 | 预期 |
|---|---|---|
| 全部满足 | 70+15+15 | 100 |
| 必备 1/2，加分 0/1，年限满足 | 35+0+15 | 50 |
| 没有加分项和年限要求，必备 1/2 | 只剩必备，权重放大 | 50 |
| 必备 2/2，年限 1/2，无加分项 | (70+7.5)÷85×100 | 91 |

→ 先运行，看到**红**（导入失败）→ 写 `schemas.py`、`scoring.py` → **绿**（16 个通过）。

**评分公式**：`总分 = Σ(权重 × 满足率) ÷ Σ(参与的权重) × 100`，权重 必备 70 / 年限 15 / 加分 15。**不存在的维度不参与，剩余权重按比例放大**，避免“没有加分项的岗位白送或被扣分”。

**一个重要的设计转变**：最初让模型自己输出总分，后来意识到小模型做加权计算不可靠，同一输入可能给出 72 或 85，也没法解释。于是 `MatchReport` 里**故意没有总分字段**，改成“模型逐项判断，代码算分”。

### 第 3 步：接入模型

**3.1 先探测，再设计**：用两个很短的调用，检查 DeepSeek-V4-Flash 的正文是否干净（有没有混进思考过程）、输出能否被 `PydanticOutputParser` 解析。结果干净，才继续往下写（见难题 1）。

**3.2 简历抽取链**：`make_structured_chain(llm, schema, prompt)` 通用工厂，`llm` 作为参数传入（**依赖注入**），测试时换假模型。提示词里写了防错规则：学历只能是固定几个值、不要把公司名当学校、年限只算实习和工作。

**3.3 岗位描述抽取链**：区分“必备”和“加分”、“优先”不算硬性门槛、软素质（沟通能力）不当作技能。真实运行后发现**同一份 JD 每次抽出的技能写法不一致**（难题 3），于是收紧提示词并加了缓存。

**缓存**：同一份 JD 只抽一次。键是 JD 原文的哈希，文件里记录**提示词版本**——提示词一改，旧缓存自动作废（否则会悄悄继续用旧结果）。损坏的缓存当作没有，重新抽取并修复。

**3.4 逐项对比链**：给模型看**简历原文**（而不是抽取后的摘要，因为抽取会丢细节，也为后面核对依据做准备），要求依据“直接摘抄原文”。用 `align_checks` 把模型的结果和 JD 技能清单对齐（见难题 4）。

**3.5 依据核对**：模型说“满足”时，检查它给的依据是否出自简历（见难题 5）。

### 第 4 步：完整流程和命令行 `match`

`pipeline.py` 把抽取、判断、算分串起来，`report.py` 排版，`cli.py` 做入口。命令行先检查文件、再创建模型（文件有问题时不该去连网络）；失败只显示错误类型，避免报错里带出 key 片段。

**第一次端到端真实运行**：大模型应用岗 82 分、NLP 算法岗 24 分、Java 岗 3 分，排序符合直觉；同时**暴露了一个单元测试没发现的 bug**（难题 6）。

### 第 5 步：岗位库推荐 `recommend`

- `library.py`：每个岗位的 ID 是内容哈希；`sync` 只给**新增**的岗位算 embedding，改过的“删旧加新”，被删除的移除（原项目每次 `rmtree` 重建，岗位多了会又慢又贵）。
- `recommend.py`：简历只抽取一次；检索前 k 个；逐个评分；**按总分排序**。
- 真实运行：排名 82 / 33 / 24 / 3；第一次同步“新增 4”，第二次“沿用 4”。

### 第 6 步：院校名单（爬取教育部页面）

**起因**：名单里原来只有 7 所示例学校，绝大多数学校会显示“无法判断”。

做法：只抓教育部的 985、211 两个公开页面；先读 `robots.txt`；**数量校验**（985 应为 39、211 含 985 应为 112）；默认只预览，加 `--write` 才写文件；抓到空结果时**绝不覆盖现有名单**。真实运行：985 共 39 所、211（不含 985）73 所、合计 112，**零警告**。

随后的讨论里，我们也检查了 BOSS 直聘和前程无忧的 `robots.txt`（见难题 12）。

### 第 7 步：Streamlit 网页（再分五小步）

1. **共用层**：`documents.py`（读文件，GBK 兼容，扫描件提示）、`services.py`（组装服务）。命令行也改成用它们，保证两边行为一致。
2. **最小页面**：上传或粘贴二选一；用 `AppTest` 无头测试。
3. **结果展示**：分数卡片 + 进度条 + 表格。
4. **岗位库推荐标签页**：排名表、可展开的详细报告、k 滑块。
5. **在真实浏览器里检查**：走了两个标签页，并检查了桌面和手机宽度，发现并修复了两个只有实际打开才看得出的问题（难题 10、11）。

## 5. 遇到的难题与解决办法

### 难题 1：不知道新模型的输出是否“干净”

**现象**：DeepSeek-V4-Flash 带“推理模型”标签，推理模型常把思考过程混进正文，会让 JSON 解析失败。我对这个新模型没有先验知识。

**做法**：不猜，先写一个探测脚本，调用两次：一次普通对话，一次结构化抽取；检查有没有 `<think>`、有没有 `reasoning_content`，并用 `PydanticOutputParser` 实际解析。

**结果**：正文干净，解析成功。**教训**：对没把握的外部依赖，先花几分钟实测，再基于结果设计，避免后面返工。

### 难题 2：模型做算术不可靠

**现象/担忧**：让模型直接给总分，同一输入可能每次不同，也无法解释分数从何而来。

**解决**：模型只做逐项判断，总分由代码算（见第 2 步）。**效果**：每个分数都能追溯到具体哪一项技能、依据是什么；评分部分有 19 个确定性的单元测试。

### 难题 3：同一份岗位描述，每次抽出的技能写法不一致

**现象**（真实运行发现）：同一个 JD 抽 3 次，有时“LangChain”、有时“LangChain或类似框架”；有时 4 项、有时 5 项。

**为什么要紧**：总分 = 满足项数 ÷ 总项数，分母变了，同一个人的分数就变了。

**解决（两层）**：

1. 提示词加规则：每一项只写一个技术名词；“A 或 B”、“A 和 B”要拆开；不带括号和“经验、了解”等程度词，并给了正反示例。
2. **缓存岗位抽取结果**：岗位描述是静态的，抽取一次后固定下来。

**效果**：复合项和括号消失；12 次里仍有 1 次少抽了一项（Python），所以才需要缓存兜底。读缓存 5.8–6.8 毫秒，调用模型 1.5–2.6 秒。

**副作用（已记入已知局限）**：把“有模型训练**或**微调经验”拆成两项，会变成两项都必备，对这类岗位偏严。

### 难题 4：模型漏判、多判、改写技能名

**现象**：要求模型对每项技能输出判断，但它可能漏掉一项、多编一项、或改写技能名，而评分的分母必须是“JD 里有几项”。

**解决**：`align_checks`，纯代码：按 JD 顺序重排；漏掉的补成“未满足，依据：模型未给出判断”（宁可保守，不白送分）；多出的丢弃；重复的取第一个；匹配时忽略大小写和空白，**技能名以 JD 为准**。有 6 个测试覆盖这些情况。

### 难题 5：模型可能编造依据——以及“严格核对”会误伤一半

**设想**：模型说“满足”时，依据必须能在简历原文里逐字找到。

**真实数据推翻了它**：判为“满足”的依据里，只有 **10/19** 能逐字找到。多数是模型给原文**加了括号注释**，比如 `Chroma（属于向量数据库）`，判断本身是**对的**。如果严格比对，会把正确判断扣分。

**解决（容错版）**：把依据按标点和空白拆成片段，只要有一个“有分量”的片段（长度 ≥ 4，或纯英文数字 ≥ 3，如 `SQL`、`RAG`）出现在原文里，就算有依据。完全对不上才降级为“依据存疑”，并保留模型原话。

**诚实的局限**：这道保险在真实运行中**一次都没触发**，所以“能拦住编造”只在人造的案例上验证过；而且它**拦不住“引用真实但推理不对”**的判断。

### 难题 6：单元测试全绿，真实运行才暴露的 bug

**现象**：算法岗要求“985/211优先”，北京邮电大学属于 211，却被判成“不满足”。

**原因**：代码看到“985”就按 985 门槛判断，忽略了后面的“211”。我写的测试只测了“985 学校对 985/211”和“211 学校对纯 985”，恰好漏掉这个组合。

**解决**：先补两个会失败的测试复现 bug，再改成“要求里提到多个层次时，取最低的作为门槛”。**教训**：单元测试的价值取决于你想到了哪些场景；真实数据能暴露你没想到的组合，所以要两者都做。

### 难题 7：怎么在不联网、不花钱的情况下测试大模型应用

**解决**：**依赖注入** + 假模型。所有链的 `llm` 都是参数；测试里用 `FakeListChatModel`（按预设返回固定文本）、`DeterministicFakeEmbedding`（相同文本得到相同向量）。

**证明“命中缓存时没有再调用模型”的技巧**：给假模型预设**两个不同**的回复 A、B。第一次拿到 A；如果第二次又去调用了模型，就会拿到 B，测试会发现。证明“没变的岗位不会重复计算 embedding”则用一个“计数 embedding”记录被计算过的文本。

### 难题 8：读文件的编码和空文件

**现象**：Windows 记事本默认保存的 txt 是 GBK，只认 UTF-8 的程序会读成乱码；扫描件 PDF 提取不到文字，模型会对着空文本瞎分析。

**解决**：`documents.py` 先试 UTF-8（含 BOM），再试 GB18030；空文件、扫描件 PDF、损坏的 PDF 都抛出带明确说明的 `DocumentError`（“PDF 里没有提取到文字，可能是扫描件”）。

### 难题 9：在 PowerShell 里做自动化时的中文乱码

**现象**：把含中文的 Python 代码通过管道传给解释器，PowerShell 的编码处理会把中文弄坏，报 `UnicodeEncodeError`。

**解决**：把脚本写成文件再运行；设置 `PYTHONIOENCODING=utf-8`；程序入口里把 `stdout`/`stderr` 设成 UTF-8。

### 难题 10：网页上“依据”列被截断

**发现方式**：在**真实浏览器**里看到的。`st.dataframe` 的单元格不换行，模型给的依据比较长，被切掉了，而“依据”恰恰是页面上最重要的信息。

**解决**：改用 `st.table`（会换行）；它默认显示行号，就把第一列设成索引。**这个问题 `AppTest` 测不出来**——它能证明元素存在、数值对，看不出排版。

### 难题 11：手机宽度下，排名表看不到“总分”

**发现方式**：缩小到手机宽度检查时发现，“总分”列原本排第四，被挤出了屏幕。

**解决**：先写测试（`list(row)[:3] == ["排名","总分","岗位"]`），再把总分调到第二列，并在浏览器里复查。

### 难题 12：数据从哪来（爬虫的取舍）

想按专业分类、扩大岗位库时遇到：数据从哪来？

- **教育部的两个公开页面**：没有 `robots.txt` 限制，数量可校验，适合脚本抓取（已做）。
- **BOSS 直聘**：读了它的 `robots.txt`，对所有爬虫禁止 `/*?*`（任何带查询参数的网址，也就是搜索和翻页）、求职者端推荐列表和数据接口。要拿到一批岗位必须先走这些路径，**规则本身就堵住了**，所以没有写。
- **前程无忧**：三个域名都没有发布 `robots.txt`（请求返回的是普通网页），但**没有找到用户协议原文**，岗位页是否要登录、有没有反爬也没有实测，所以没有写。
- **原则**：爬虫自己要遵守 `robots.txt`；验证码、登录和反爬不绕；只存岗位文字，不存联系方式；不提交数据；个人少量自用和大规模商业抓取风险完全不同。

### 难题 13：几个小插曲（也值得记）

- **在 PyCharm 里点绿色按钮运行 `app.py`**：只会打印一串 `missing ScriptRunContext` 就退出，因为必须用 `streamlit run app.py`。已写进 README。
- **Streamlit 首次运行问邮箱**：是欢迎提示，不是错误，按回车留空即可。
- **在浏览器里测试输入**：我用 `form_input` 给文本框赋值，页面却报“请上传简历”，因为它改的是显示值，Streamlit 的内部状态没感知到；改用真实键盘输入就正常了。**教训**：自动化测试的方式本身也可能是误差来源，先排除再下结论。点击落空则是坐标点偏了，改用元素引用一次就成功。
- **一次口误**：我在讨论“市面上怎么做”时说项目有“189 个测试”、“16 次提交”，都是错的，实际是 **153 个测试、15 次提交**，本文用的是实测数。

## 6. 怎么测试的

测试分五层，每层回答不同的问题：

| 层 | 工具 | 回答什么问题 | 数量 |
|---|---|---|---|
| ① 纯函数单元测试 | pytest | 给定输入，计算/整理对不对？（评分、对齐、依据核对、表格行整理、名单解析） | 大部分 |
| ② 假模型的链测试 | `FakeListChatModel` | 链的接线对不对？提示词里有没有带上字段说明和规则？能不能解析普通 JSON 和 ```` ```json ```` 代码块？ | — |
| ③ 假 embedding 的检索测试 | `DeterministicFakeEmbedding` | 增量同步对不对？没变的岗位有没有重复计算？检索顺序、k 大于库大小、空库？ | 8 个 |
| ④ 页面交互测试 | Streamlit `AppTest` | 点按钮后有没有结果？空输入有没有提示？失败时是否只显示错误类型（不泄露 key）？旧结果是否被清掉？ | 13 个 |
| ⑤ 真实运行 | 真实模型、真实 embedding、真实浏览器 | 模型判得准不准？页面好不好看？ | **手动**，不是自动测试 |

**测试驱动的节奏**：每个功能先写测试 → 运行 → 看到**红** → 写实现 → **绿**。这个“红”很重要：它证明测试真的在检查东西，而不是永远通过。

**测试的几个设计习惯**：

- 手算好的期望值（如 41 分、91 分）写进测试，而不是用代码算期望；
- 断言**状态码**（`满足/不满足/无法判断/未要求`），不断言整句中文，文案怎么改都不影响测试；
- 院校名单作为**参数**传入，测试不依赖 `data/schools.json` 的内容，所以你补全名单不会让测试失败；
- 专门写了“失败时不泄露 key”的测试：让假链抛出带“secret-key”字样的异常，断言页面上没有这串内容。

### 7.3 这些结果**不能**说明什么

- 没有标注测试集，所以**没有准确率这个数字**。

## 8. 设计合理性的评价

对每个关键决策，说清楚“为什么合理”和“代价”：

| 决策 | 合理在哪 | 代价 / 风险 |
|---|---|---|
| **模型判断，代码算分** | 分数确定、可复现、可追溯到具体技能；评分逻辑可以充分单元测试 | 分数只反映“满足了几项”，不反映“满足得多深”（精通和了解都算满足）；所有技能权重相等 |
| **岗位技能清单以 JD 为准，用代码对齐** | 分母不受模型波动影响；模型漏判时保守处理 | 依赖岗位抽取的质量，抽取错了，分母就错了 |
| **缓存岗位抽取** | 同一份 JD 结果固定；省时间省钱；读缓存快约 300 倍 | 改提示词后缓存自动作废，包括手工修正过的内容 |
| **容错版依据核对** | 严格逐字核对会误伤约一半正确判断；容错版只拦完全对不上的 | 拦不住“引用真实但推理不对”；真实运行中没触发过，有效性只在人造案例上验证 |
| **向量检索只做粗筛，最终按总分排序** | 检索只说明“话题相近”，不说明“够不够格”；实测 NLP 算法岗检索距离最远，最终得分却高于 Java 岗 | 检索挑不进来的岗位不会被评分，**k 太小会漏掉更合适的岗位**；岗位库只有 4 个，粗筛基本没发挥作用 |
| **岗位按内容哈希增量同步** | 只给新增岗位算 embedding；改过的“删旧加新” | 两个文件内容完全相同会被当成一个 |
| **学历和学校单独展示，不计入总分** | 名称匹配会出错，自动据此拉低分数会误伤；也避免“唯学校论” | 报告里“985/211优先”本质是偏好，却显示“不满足”，措辞偏重 |
| **名单里查不到返回“无法判断”，不是“不满足”** | 名单可能不全、写法可能不一致，不能把“没收录”当成“不达标” | 对普通本科候选人，**确实不是 985/211，却也只显示“无法判断”**（需要全国高校名单才能分清） |
| **依赖注入 + 假模型** | 153 个测试全部离线，不花钱，几秒跑完 | 假模型证明不了“模型判得准”，这部分只能靠真实运行 |
| **网页和命令行共用 `services` 和 `documents`** | 两边行为一致，不会各写一份 | — |
| **不绕过验证码和 `robots.txt`** | 合规；也避免个人信息和条款风险 | 拿不到 BOSS 直聘这类平台的大批量数据 |

## 9. 还没解决的问题

按重要性排序：

1. **没有标注测试集**：所有“模型判得准不准”的说法都只建立在 1 份简历、4 个岗位上。这是和成熟项目差距最大的地方。
2. **校名是精确匹配**：简历写“中国地质大学（武汉）”、“北邮”会被判为“未收录”；教育部名单是 2005、2006 年的版本，之后改过名的学校（如国防科学技术大学、第二军医大学）会匹配不上。
3. **院校只有 985/211 两个层次**：分不清“确实不是 985/211”和“名单里没有这个名字”；需要全国高校名单（含本科/专科层次）。
4. **没有做偏见测试**：模型判断时看的是整份简历原文，含姓名、性别、学校信息。研究里有“换姓名或性别后分数是否稳定”的反事实测试，这个项目还没做。
5. **模型给的依据有时很笼统**：例如把整行技能清单摘抄下来当依据，依据核对只检查它出自原文，不检查它贴不贴切。
6. **岗位库太小**：只有 4 个样例，推荐几乎没有选择余地；按专业分类的设计也还没做（需要先有数据）。
7. **推荐是逐个串行评分**，岗位多了会很慢。
8. **`requirements.txt` 没有锁版本**。
9. “A 或 B”被拆成两项都必备，对这类岗位偏严；软素质完全不参与评分。

## 10. 这一天学到的东西

1. **让模型做它擅长的（理解、判断），让代码做它擅长的（计算、对齐、校验）**。这是整个项目最重要的设计原则。
2. **对不确定的东西先实测**：新模型的输出是否干净、严格核对会不会误伤，都是先看数据再决定设计。
3. **测试驱动要看到“红”**：红证明测试有效。
4. **依赖注入让大模型应用可测试**：把 `llm`、`embedding`、缓存都作为参数传入，测试时换成假的。
5. **单元测试全绿 ≠ 没有 bug**：985/211 的 bug、依据被截断、总分在手机上看不到，都是真实运行才暴露的。
6. **数字要核对，别凭印象**：数量校验（39/112）帮我们发现数据对不对；我自己也说错过测试数量，被实测数据纠正。
7. **合规是设计的一部分**：先读 `robots.txt`，不绕过反爬，不存个人信息，数据不提交。
8. **诚实地写局限**：README 的“已知局限”和本文第 7.3、第 9 节，比一份漂亮的功能清单更有价值。

**面试里可以这样讲这个项目**：

> 两阶段岗位推荐：向量检索粗筛候选岗位，大模型逐项判断技能是否满足并给出依据，最终分数由代码按权重计算，所以每个分数都能追溯到具体技能。可靠性方面做了岗位技能清单对齐、依据核对、岗位抽取缓存；153 个测试全部离线，通过依赖注入和假模型实现。局限是评估样本还很小，没有标注测试集。
