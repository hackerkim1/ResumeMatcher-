## 1. 起点：为什么做这个项目

**背景**：刚学完 LangChain 的调用链（`prompt | llm | parser`），之前做过一个知识库问答（RAG）小项目，想再做一个项目巩固。

**选题过程**：先列了几个候选（信息抽取器、多意图路由、长文档总结、升级原项目、工具调用 Agent），又问“有没有实际实用价值的”，最后选了**简历 × 岗位匹配分析器**：输入简历和岗位描述，输出匹配分数、技能缺口、修改建议和面试题。

**一个值得记下来的追问**：“这些用 AI 也能做吧，为什么要做这种项目？”

答案是：做项目的价值不在“做出一个比 ChatGPT 更好的产品”，而在于学会**怎么让大模型可靠地干活**：检索回来的内容不相关怎么办、模型编造怎么发现、输出格式不对怎么兜底、成本和速度怎么控制。这些只有亲手做、亲手踩坑才会懂。选项目的标准也因此变成：**选“有固定流程、要批量、要集成”的任务，别选“聊天式的通用能力”**。

**开发方式**：按真实开发流程，**先搭框架，再逐步填充，每步可验证**；每个功能都按**测试驱动**（先写会失败的测试，看它变红，再写实现，变绿）。

## 2. 最终的框架

### 2.1 三条流程

**① 单岗位匹配 `match`**（没有检索）：

```
简历文本 ──► 简历抽取链 ──► ResumeInfo ─────────────┐
                                                     ├──► 代码算分 ──► 报告
岗位描述 ──► 岗位抽取链(带缓存) ──► JobRequirement ──┤
                                                     │
简历原文 + 岗位技能清单 ──► 逐项判断链 ──► 对齐 ──► 依据核对 ──┘
```

**② 岗位库推荐 `recommend`**（向量检索 + 大模型判断）。岗位有两个来源：样例岗位（`data/jobs/*.txt`）和抓取的岗位（`jobs.jsonl`），各用**独立的向量集合**：

```
简历 ──► 抽取一次 ──► 拼成“技能+项目”查询文本
                          │
                          ▼
   Chroma 向量检索（bge-m3）+ 可选的【专业方向】元数据过滤 ──► 前 k 个候选岗位
                          │
                          ▼
         对每个候选岗位：抽取 → 逐项判断 → 对齐 → 核对 → 代码算分
                          │
                          ▼
                 按【总分】排序（不是按检索距离）
```

**③ 抓取岗位 `crawler`**（下午新增，仅供个人学习）：

```
tracks.py：9 个专业方向 → 27 个关键词
        │
        ▼ 先读 robots.txt（被禁止就一个请求都不发）
国聘列表接口（每个关键词 ≤ 11 条，总量 ≤ 300）──► 丢弃联系人和内部 ID ──► 去重
        │
        ▼
data/crawled/iguopin/jobs.jsonl（一个文件，一行一个岗位：完整正文 + 专业方向等元数据）
        │
        ▼ 向量化，进入 ②
```

### 2.2 贯穿全项目的两条原则

1. **模型负责理解，代码负责计算和约束**。

| 谁做 | 做什么 |
|---|---|
| 大模型 | 把简历、岗位描述抽成结构化数据；逐项判断“简历是否体现了这项技能”并摘抄依据；写修改建议和面试题 |
| 代码 | 技能清单对齐、依据核对、总分计算、学历和学校检查、岗位库同步、排序、**抓取时的所有限制** |

原因：模型做算术和精确匹配不可靠、结果有波动；代码结果确定、可测试、可解释。

2. **凡是“约束”，都写进代码并写测试，不靠自觉**。爬虫的请求间隔、总量上限、遇到登录就停、不存联系人，每一条都有对应的测试，而不是写在文档里让人记得遵守。

## 3. 技术栈与选型理由

| 技术 | 用在哪 | 为什么选 | 代价 / 替代方案 |
|---|---|---|---|
| **Python 3.11 + 每个项目独立 venv** | 全部 | 生态完整；独立虚拟环境避免和别的项目互相污染依赖 | `requirements.txt` 没有锁版本，将来依赖升级可能出问题（见第 10 节） |
| **硅基流动 + DeepSeek-V4-Flash** | 所有模型调用 | 已有 key；接口兼容 OpenAI 格式，所以直接用 `ChatOpenAI`，只改 `base_url` 和 `model`；一开始用 Qwen2.5-7B，为提高准确度换成更大的模型 | 这个模型很新，我对它没有先验知识，所以**实测**了它的输出（见难题 1）；换模型只要改 `.env` 里的 `CHAT_MODEL` |
| **LangChain（LCEL 管道）** | 链的编排 | 项目目标就是巩固调用链；`prompt \| llm \| parser` 结构清晰；`FakeListChatModel` 让离线测试成为可能 | 项目只用到它很小的一部分；如果不为练习，直接调用 SDK 依赖更少 |
| **Pydantic + `PydanticOutputParser`** | 结构化输出和数据校验 | 同一份定义既生成给模型的格式要求，又负责校验结果；对**任何**模型都通用 | 没选 `with_structured_output`，因为它依赖模型支持工具调用，小模型不一定稳 |
| **Chroma + BAAI/bge-m3** | 岗位库的向量索引与检索 | 本地持久化、零部署；bge-m3 中文能力强；**支持元数据过滤**，所以能“只在某个专业方向里检索”；同一个文件夹里可以放多个集合，样例岗位和抓取的岗位互不影响 | 适合小规模（几百到几千条）；再大要考虑别的向量库 |
| **JSON Lines（`jobs.jsonl`）** | 抓取岗位的存储 | 一个文件、一行一个岗位、可以只追加、坏了一行不影响其他行；用标准库就能读写，人也能直接看 | 数据量到几十万时要换数据库；追加时要先读出已有的编号来去重 |
| **PyMuPDF（`pymupdf`）** | 读 PDF | 对中文 PDF 支持好；能判断“没有文字层”（扫描件） | 扫描件需要 OCR，目前只提示 |
| **Streamlit** | 网页 | 熟悉；纯 Python；自带 `AppTest` 可以无头测试交互 | 每次交互重跑整个脚本，要用 `cache_resource` 和 `session_state` 避免重复创建模型、丢失结果 |
| **pytest + 假模型/假 embedding/假网络** | 测试 | `FakeListChatModel`、`DeterministicFakeEmbedding` 让链、检索、增量同步都能不联网、不花钱地测试；爬虫的网络和睡眠也作为参数传入，测试里换成假的 | 假的只能证明“接线对”，不能证明“模型判得准”或“网站真的会这样返回” |
| **标准库 `urllib`、`html.parser`、`urllib.robotparser`** | 抓取院校名单、抓取岗位、解析 robots.txt | 只抓几个页面，没必要引入新依赖；`robotparser` 现成地解析 `robots.txt` | 页面更复杂时才需要 requests / BeautifulSoup |
| **pandas** | 仅用于 `st.table` 的索引 | 已安装；用来把第一列设为索引，去掉默认行号 | 只用了一点点，是个“顺手”的依赖 |
| **python-dotenv** | 读 `.env` | key 不写进代码；`.env.example` 做模板 | — |
| **git（21 次提交）** | 版本管理 | 每个提交只做一件事，历史就是开发过程的目录；`git worktree` 还能把每个提交单独检出来验证 | — |

## 4. 开发时间线

### 上午：核心功能

#### 第 0 阶段：规划与分层

先想清楚模块各管什么，再动手。核心决定：

- 按**职责**分层，不按“我先写哪个”；
- `scoring.py` 不依赖模型 → 最容易测试 → **最先写**；
- `config.py` 是唯一读环境变量的地方；
- `.env.example`（模板）和 `.env`（真 key，被忽略）分开，`.gitignore` 先写好。

#### 第 1 步：项目骨架

建目录、空模块（只写职责说明）、`requirements.txt`、`.gitignore`、README、`git init`。

#### 第 2 步：数据结构 + 评分（测试驱动）

**先写测试，我手算了答案**：

| 场景 | 手算 | 预期 |
|---|---|---|
| 全部满足 | 70+15+15 | 100 |
| 必备 1/2，加分 0/1，年限满足 | 35+0+15 | 50 |
| 没有加分项和年限要求，必备 1/2 | 只剩必备，权重放大 | 50 |
| 必备 2/2，年限 1/2，无加分项 | (70+7.5)÷85×100 | 91 |

→ 先运行，看到**红**（导入失败）→ 写 `schemas.py`、`scoring.py` → **绿**（16 个通过）。

**评分公式**：`总分 = Σ(权重 × 满足率) ÷ Σ(参与的权重) × 100`，权重 必备 70 / 年限 15 / 加分 15。**不存在的维度不参与，剩余权重按比例放大**，避免“没有加分项的岗位白送或被扣分”。

**一个重要的设计转变**：最初让模型自己输出总分，后来意识到小模型做加权计算不可靠，同一输入可能给出 72 或 85，也没法解释。于是 `MatchReport` 里**故意没有总分字段**，改成“模型逐项判断，代码算分”。

#### 第 3 步：接入模型

- **3.1 先探测，再设计**：用两个很短的调用，检查 DeepSeek-V4-Flash 的正文是否干净、输出能否被 `PydanticOutputParser` 解析。结果干净，才继续往下写（难题 1）。
- **3.2 简历抽取链**：`make_structured_chain(llm, schema, prompt)` 通用工厂，`llm` 作为参数传入（**依赖注入**），测试时换假模型。
- **3.3 岗位描述抽取链**：区分“必备”和“加分”、“优先”不算硬性门槛、软素质不当作技能。真实运行后发现**同一份 JD 每次抽出的技能写法不一致**（难题 3），于是收紧提示词并加了缓存（键是 JD 原文的哈希，文件里记录提示词版本，提示词一改就作废）。
- **3.4 逐项对比链**：给模型看**简历原文**，要求依据“直接摘抄原文”，用 `align_checks` 把模型的结果和 JD 技能清单对齐（难题 4）。
- **3.5 依据核对**：模型说“满足”时，检查它给的依据是否出自简历（难题 5）。

#### 第 4 步：完整流程和命令行 `match`

`pipeline.py` 串起来，`report.py` 排版，`cli.py` 做入口。命令行先检查文件、再创建模型；失败只显示错误类型。第一次端到端真实运行得到 82 / 24 / 3 分，同时**暴露了一个单元测试没发现的 bug**（难题 6）。

#### 第 5 步：岗位库推荐 `recommend`

- `library.py`：每个岗位的 ID 是内容哈希；`sync` 只给**新增**的岗位算 embedding，改过的“删旧加新”，被删除的移除。
- `recommend.py`：简历只抽取一次；检索前 k 个；逐个评分；**按总分排序**。
- 真实运行：排名 82 / 33 / 24 / 3；第一次“新增 4”，第二次“沿用 4”。

#### 第 6 步：院校名单

名单里原来只有 7 所示例学校。做法：只抓教育部的 985、211 两个公开页面；先读 `robots.txt`；**数量校验**（985 应为 39、211 含 985 应为 112）；默认只预览，`--write` 才写；抓到空结果时**绝不覆盖现有名单**。真实运行：985 共 39 所、211（不含 985）73 所，**零警告**。

#### 第 7 步：Streamlit 网页（五小步）

共用层（`documents.py`、`services.py`）→ 最小页面 → 结果展示 → 岗位库推荐标签页 → **在真实浏览器里检查**，发现并修复两个显示问题（难题 10、11）。

#### 上午收尾：开发日记第一版、推送

写了第一版日记并提交；清理缓存目录；检查历史和已跟踪文件里没有任何疑似 API key（0 行）。项目没有配置远程仓库，也没装 GitHub CLI，所以推送这一步由你在自己的终端里完成（登录凭据我不处理）。**我没有核对过推送的结果。**

### 下午：补漏洞、做爬虫、扩大岗位库

#### 第 8 步：依据核对的第二次修复（提交 `a008c92`）

起因是后面第 10 步的集成检查：把样例简历拿去匹配一个抓来的岗位，得了 **0 分**，四项本来对的判断被标成“依据存疑”。先补会失败的测试，再修（难题 14）。

#### 第 9 步：先看看别人怎么做（讨论，没有写代码）

读了 `career-navigator` 仓库、查了市面上的简历匹配做法、讨论了岗位数据从哪来，以及“RAG 到底体现在哪”（见第 6 节）。这几次讨论直接决定了后面的设计。

#### 第 10 步：爬虫第一版（提交 `4e53bfc`）

**先选来源，再写代码**，不是对着某个网站直接写：

| 站点 | `robots.txt` | 结论 |
|---|---|---|
| BOSS 直聘 | 禁止 `/*?*`（搜索翻页）、推荐列表、数据接口 | 规则堵住了，不做 |
| 前程无忧 | 三个域名都没有发布 | 无声明，也没找到用户协议，不做 |
| 智联、猎聘 | 禁止所有带查询参数的网址和接口 | 同 BOSS，不做 |
| 国家大学生就业服务平台 | 没有发布 | 无声明，不做 |
| **国聘** | **`Disallow:` 为空，明确放行** | 可以考虑 |

然后在浏览器里**像普通访客一样**观察国聘（难题 15）：岗位列表不登录就能看；它是单页应用，数据来自 `gp-api.iguopin.com` 的接口；列表接口直接返回完整岗位描述，所以不需要逐个请求详情页。

先把**限制写进测试**，再实现：先查 `robots.txt`、请求间隔、总量上限、遇到登录或验证码立刻停且不重试、不存联系人。第一次真实试跑：**只发了 1 次岗位请求，抓到 10 条**，隐私扫描为 0。

同时发现并修了两处数据问题：专业要求里同一个专业类重复出现；有的专业要求写的是“详见职位描述”。

#### 第 11 步：你指出“全是数据分析师，其他专业怎么办”——多关键词、单文件、按方向检索

第一次试跑只用了一个关键词、10 条，所以全是数据分析。要覆盖各专业，需要多关键词，总量会超过原先约定的 100 条上限，**我没有擅自提高，而是先请你确认**：同意总量 300 条、每个关键词不超过 30 条。

设计的几个关键决定（难题 16、17、18）：

- **专业方向表** `tracks.py`：9 个方向、27 个关键词，是**我们自己定的分类**，因为国聘返回的“专业要求”字段不统一，不适合直接做过滤；
- **名额平均分配**：每个关键词的名额 = `min(30, 300 ÷ 27)` = 11 条；
- **单文件** `jobs.jsonl`：所有岗位存在一个文件里，每行含完整正文和元数据，按岗位编号去重，重复运行不会重复写；
- **独立的向量集合**：抓取的岗位用 `jobs_crawled`，样例岗位用 `jobs`，互不影响；
- **按方向过滤的检索**：方向作为 Chroma 的元数据，检索时可以限定；
- 命令行加 `--jobs-file`、`--track`，网页的推荐页加“岗位来源”和“专业方向”。

测试先行，分三次提交（`71dd801` 方向表和岗位文件、`9b411be` 爬虫、`6028ab8` 检索、命令行、网页和 README），并**逐个检出验证每个提交单独也能通过测试**（227 / 252 / 278 个）。

#### 第 12 步：真实运行

- **抓取**：`--all`，27 次请求，保留 297 条，没有被拦；
- **检索**：297 条一次性向量化；第二次“沿用 297”；按方向过滤有效；
- 同时暴露了检索和评分不一致的问题（难题 19）。

## 5. 遇到的难题与解决办法

> 难题 1 到 13 来自上午，14 到 21 来自下午。

### 难题 1：不知道新模型的输出是否“干净”

**现象**：DeepSeek-V4-Flash 带“推理模型”标签，推理模型常把思考过程混进正文，会让 JSON 解析失败。我对这个新模型没有先验知识。

**做法**：不猜，先写一个探测脚本，调用两次：一次普通对话，一次结构化抽取；检查有没有 `<think>`、有没有 `reasoning_content`，并用 `PydanticOutputParser` 实际解析。

**结果**：正文干净，解析成功。**教训**：对没把握的外部依赖，先花几分钟实测，再基于结果设计，避免后面返工。

### 难题 2：模型做算术不可靠

让模型直接给总分，同一输入可能每次不同，也无法解释分数从何而来。**解决**：模型只做逐项判断，总分由代码算。**效果**：每个分数都能追溯到具体哪一项技能、依据是什么；评分部分有确定性的单元测试。

### 难题 3：同一份岗位描述，每次抽出的技能写法不一致

**现象**（真实运行发现）：同一个 JD 抽 3 次，有时“LangChain”、有时“LangChain或类似框架”；有时 4 项、有时 5 项。

**为什么要紧**：总分 = 满足项数 ÷ 总项数，分母变了，同一个人的分数就变了。

**解决（两层）**：提示词加规则（每项只写一个技术名词，“A 或 B”要拆开，不带括号和程度词，并给了正反示例）；**缓存岗位抽取结果**（岗位描述是静态的，抽取一次后固定）。**效果**：复合项和括号消失；12 次里仍有 1 次少抽了一项，所以才需要缓存兜底。**副作用**：“有模型训练**或**微调经验”被拆成两项都必备，对这类岗位偏严。

### 难题 4：模型漏判、多判、改写技能名

评分的分母必须是“JD 里有几项”。**解决**：`align_checks`，纯代码：按 JD 顺序重排；漏掉的补成“未满足”（宁可保守，不白送分）；多出的丢弃；重复的取第一个；忽略大小写和空白，**技能名以 JD 为准**。

### 难题 5：模型可能编造依据——以及“严格核对”会误伤一半

**设想**：模型说“满足”时，依据必须能在简历原文里逐字找到。**真实数据推翻了它**：判为满足的依据里只有 **10/19** 能逐字找到，多数是模型给原文**加了括号注释**，判断本身是对的。

**解决（容错版）**：把依据按标点和空白拆成片段，只要有一个“有分量”的片段（长度 ≥ 4，或纯英文数字 ≥ 3）出现在原文里，就算有依据。完全对不上才降级为“依据存疑”。

**局限**：当时在真实运行里一次都没触发；而且拦不住“引用真实但推理不对”的判断。**随后在难题 14 里发现了它的另一个漏洞。**

### 难题 6：单元测试全绿，真实运行才暴露的 bug

算法岗要求“985/211优先”，北京邮电大学属于 211，却被判成“不满足”。**原因**：代码看到“985”就按 985 门槛判断，忽略了后面的“211”。我写的测试恰好漏掉这个组合。**解决**：先补两个会失败的测试复现，再改成“要求里提到多个层次时，取最低的作为门槛”。**教训**：单元测试的价值取决于你想到了哪些场景；真实数据能暴露你没想到的组合。

### 难题 7：怎么在不联网、不花钱的情况下测试大模型应用

**依赖注入** + 假模型。所有链的 `llm` 都是参数。**证明“命中缓存时没有再调用模型”的技巧**：给假模型预设**两个不同**的回复 A、B；第一次拿到 A，如果第二次又调用了模型就会拿到 B，测试会发现。证明“没变的岗位不会重复计算 embedding”则用一个“计数 embedding”记录被计算过的文本。

### 难题 8：读文件的编码和空文件

Windows 记事本默认保存的 txt 是 GBK；扫描件 PDF 提取不到文字。**解决**：先试 UTF-8（含 BOM），再试 GB18030；空文件、扫描件、损坏的 PDF 都抛出带明确说明的 `DocumentError`。

### 难题 9：PowerShell 里的中文乱码

把含中文的 Python 代码通过管道传给解释器，会被 PowerShell 的编码弄坏。**解决**：把脚本写成文件再运行；设置 `PYTHONIOENCODING=utf-8`；程序入口里把 `stdout`/`stderr` 设成 UTF-8。

### 难题 10：网页上“依据”列被截断

**发现方式**：在**真实浏览器**里看到的。`st.dataframe` 的单元格不换行，被切掉了，而“依据”恰恰是页面上最重要的信息。**解决**：改用 `st.table`（会换行）。这个问题 `AppTest` 测不出来。

### 难题 11：手机宽度下，排名表看不到“总分”

“总分”列原本排第四，被挤出了屏幕。**解决**：先写测试（`list(row)[:3] == ["排名","总分","岗位"]`），再把总分调到第二列。

### 难题 12：数据从哪来（爬虫的取舍）

想按专业分类、扩大岗位库时，先查各站点的 `robots.txt`，**规则本身堵住的就不做**（详见时间线第 10 步）。原则：爬虫自己要遵守 `robots.txt`；验证码、登录和反爬不绕；只存岗位文字，不存联系方式；不提交数据；个人少量自用和大规模商业抓取风险完全不同。

### 难题 13：几个小插曲

- **在 PyCharm 里点绿色按钮运行 `app.py`**：只会打印一串 `missing ScriptRunContext` 就退出，必须用 `streamlit run app.py`。
- **Streamlit 首次运行问邮箱**：是欢迎提示，不是错误，按回车留空即可。
- **在浏览器里测试输入**：我用 `form_input` 给文本框赋值，页面却报“请上传简历”，因为它改的是显示值，Streamlit 的内部状态没感知到；改用真实键盘输入就正常了。**教训**：自动化测试的方式本身也可能是误差来源。
- **一次口误**：我说过项目有“189 个测试”、“16 次提交”，都是错的，被实测数据纠正。

### 难题 14：依据核对的第二个漏洞——模型改写了依据（下午）

**现象**：拿样例简历去匹配一个抓来的岗位，得了 **0 分**：Python、机器学习、Linux、自然语言处理四项被标成“依据存疑”。但它们是对的。模型这次没有逐字摘抄，而是写成 `技能中列出Python，实习中使用Python和SQL清洗业务数据`。

**原因**：我们的核对把中英文连在一起的片段（`技能中列出Python`）当成一个整体，整体不在原文里，里面的 `Python` 被忽略了。

**解决**：除了按片段核对，再提取依据里的**英文术语**；**只要它们全部出现在简历里**，也算有依据；只要有一个简历里没有（比如编造的 `Docker`），仍然判为存疑。先补三个测试，看到红，再改。

**诚实的验证说明**：重跑同一个岗位得 26 分，但这一次模型改回了逐字摘抄，所以重跑本身证明不了修复有效。**证明它的是单元测试**，里面用的正是那段真实出现过的改写。

### 难题 15：单页应用，用普通请求拿不到岗位文字（下午）

**现象**：国聘首页只有 1363 字节：一个 `<div id="app">` 加一个脚本。

**做法**（都是像访客一样的只读观察）：

1. 在浏览器里打开页面，查看页面实际发出的请求，找到数据接口域名 `gp-api.iguopin.com`；
2. 读网站**公开下发**的前端脚本，找到接口的定义（列表是 `POST`，详情是 `GET`）；
3. 在页面里挂一个记录器，让页面**自己**发一次请求，记下请求体的格式；
4. 照同样的格式只请求 3 条，看返回的数据结构。

**收获**：列表接口**直接返回完整岗位描述**，所以不用再逐个请求详情页；返回里还有专业要求、类别、学历、薪资，**也有联系人**（所以白名单只保留需要的字段）。**关键词参数名**是在页面里点一次搜索、从请求体里看到的，不是猜的。

**没搞清楚的**：用户协议没找到（页面里没有入口，关于我们的文档接口里只有联系方式和营业执照，网上也搜不到）。**这一条我无法判断，请使用者自己确认。**

### 难题 16：27 个关键词 × 30 条 = 810，远超 300 的总量上限（下午）

**问题**：如果每个关键词都抓满 30 条，前面的方向会把总量吃光，**后面的医药、法学、语言一条都抓不到**。

**解决**：总量**平均分配**：每个关键词的名额 = `min(30, 300 ÷ 关键词个数)` = 11，总共最多 297 条。再加两道兜底：每个关键词最多翻 3 页（防止“全是过期岗位”时无限翻页）；一次运行最多 60 次请求（即使程序出 bug 也不会无限请求）。**测试**专门覆盖：名额均分、受每个关键词上限约束、每个关键词一页都不超过全局请求上限。

### 难题 17：真实数据比想象的脏（下午）

- 同一个专业类在一个岗位里出现两次 → 去重并保持顺序；
- 专业要求写“详见职位描述” → 当作“不限”；
- 117 条没有写具体专业 → 所以我们**不依赖国聘的专业字段做过滤**，而是用自己的“专业方向”（按搜索关键词归类）。

### 难题 18：共用的向量索引，一个同步会把另一个的岗位删掉（下午）

**问题**：样例岗位和抓取的岗位如果放在同一个集合里，每次同步都会把“不在当前目录里的”岗位当成过期删掉，两边会互相覆盖。这个隐患在上午就指出过，抓取之后真正需要解决了。

**解决**：抓取的岗位用**独立的集合** `jobs_crawled`。**测试**：同步样例岗位之后，抓取岗位的数量不变。

### 难题 19：检索和评分不一致，检索被“前端”带偏（下午，**未解决**）

**现象**：用样例简历（Python、LangChain、RAG 项目）在 297 条里检索前 5 个：

| 方式 | 结果 |
|---|---|
| 不限方向，k=5 | 1 个数据分析岗（31 分）+ **4 个前端开发岗（0 到 1 分）** |
| 限定“计算机/软件”，k=8 | **算法工程师 16 分**排第一，前端 10 分，后端 9 分 |

**怎么理解**：

- 更对口的算法工程师在第一次检索里**没有进入候选**。很可能因为查询文本里“Streamlit、做前端”出现了两次，把检索拉向前端（这是我的推测，没有做对照实验）；
- 限定方向后它才出现，而且它的**检索距离在 8 个里最远，得分却最高**：这正是“检索只管话题相近，评分才管够不够格”的真实例子；
- 所以 **k 要取得比想看的名次大**，岗位库越大越要如此。

**没做的**：改进查询文本（只用技能、不带项目描述，或多个查询合并）。

### 难题 20：分三次提交，第一次提交单独不能通过测试（下午）

**问题**：`test_tracks.py` 里有个测试要从爬虫里导入新的 `MAX_TOTAL_JOBS`，而这个常量在第二次提交才引入，所以第一次提交单独检出就会报错。

**解决**：把这个测试挪到爬虫的测试文件里（它本来就是在检查爬虫的总量上限）。**验证**：用 `git worktree` 把三个提交分别检出到临时目录，用项目的虚拟环境各跑一遍完整测试：227、252、278 个全部通过，之后删除临时目录。**上午只验证过最终状态，这次是逐个提交验证。**

### 难题 21：几个自己的小失误（下午）

- 写了一个测试，假数据 `total=10` 而主程序默认页大小是 20，会在第 1 页就判断“已取完”而正常结束，根本走不到我想测的第 2 页失败；跑之前自己发现并改成了 `total=100`；
- 在 PowerShell 命令的标题里用了**中文弯引号**，被当成字符串边界而报语法错误，去掉后重跑；
- 用 `Select-Object -First` 截断输出，管道被提前关闭，退出码显示 255，**不是程序出错**，容易被误判。

## 6. 今天的几次重要讨论

这些讨论没有直接产生代码，但改变了设计和我对项目的描述。

### 6.1 “这个项目用到 RAG 了吗？”

**真实情况**：

- 有向量化（`bge-m3`）、有向量检索（Chroma），**没有文档切分**：每个岗位描述当作一个完整文档。原因是岗位描述只有几百字，切开会把“岗位名”“必备技能”“加分项”拆散，丢掉上下文。
- 只有 `recommend` 用到检索；`match` 完全没有。
- **严格说也不是经典 RAG**：经典 RAG 是“检索资料 → 塞进提示词 → 生成回答”，而这里检索回来的岗位是**被评分的对象**，不是给模型参考的资料。更准确的叫法是“**向量检索 + 大模型重排**”。

**对描述项目的影响**：不要说“完整的 RAG 流程”，要说“向量检索做粗筛，不切块”，并能解释为什么不切。

### 6.2 “存成一个文件，就体现了 RAG 吗？”

不是。**RAG 体现在“向量化 + 检索”，不在于数据存成几个文件。** 单文件 `jobs.jsonl` 只是数据的载体，方便管理；真正体现检索的，是**带元数据过滤的向量检索**：同一个向量库里，按专业方向缩小范围。

### 6.3 市面上同类项目怎么做

| 做法 | 特点 |
|---|---|
| 关键词和规则匹配（传统招聘管理系统） | 简单，认不出同义词 |
| 向量相似度（如 Resume-Matcher） | 快，只能说“像不像”，说不出缺什么 |
| **两阶段：向量粗筛 + 大模型精排**（如 strata-match） | 兼顾速度和解释性，**和本项目的 `recommend` 同一结构** |
| 学习排序（大平台，用历史投递和录用数据） | 效果最好，个人拿不到数据 |

本项目在**技术结构**上与两阶段方案一致，多做了几件开源项目里不常见的事：模型只判断、代码算分；依据核对；技能清单对齐；缓存；离线测试。**差距在评估**（没有标注测试集），不在功能。

另外查到的研究里，有不少是关于**招聘排序中的偏见**的（性别、种族），以及“换姓名或性别后分数是否应该基本不变”的反事实测试。本项目**没有做过**这类测试，见第 10 节。

### 6.4 看别人的项目：career-navigator

只读不运行。要点：

- **它没有岗位库**，岗位由智能体**运行时现场联网查**，规则要求每次重新验证岗位仍在招；仓库里只有 10 条占位的测试数据；
- 它的排序脚本只做加权、分组和贴标签，**5 个维度的分数由模型给出**；
- 它的文档**没有谈抓取方式、`robots.txt` 或平台条款**，合规问题没有解决，只是没写出来。

**可借鉴但没做的**：岗位记录带来源和验证时间；用户自定义的排除规则；薪资只有在样本足够时才给参考。

### 6.5 “岗位大全”和数据来源

书籍（职业分类大典、岗位说明书范本）不适合当数据来源：格式和内容不匹配，而且有版权。公开数据集我没有找到合格的中文岗位描述数据集（来源和许可都不明确）。所以最终选择了**在合规前提下小规模抓取**，并把所有限制写进代码。

## 7. 怎么测试的

测试分六层，每层回答不同的问题：

| 层 | 工具 | 回答什么问题 |
|---|---|---|
| ① 纯函数单元测试 | pytest | 给定输入，计算/整理对不对？（评分、对齐、依据核对、表格行整理、名单解析、岗位解析、`jobs.jsonl` 读写） |
| ② 假模型的链测试 | `FakeListChatModel` | 链的接线对不对？提示词里有没有带上字段说明和规则？ |
| ③ 假 embedding 的检索测试 | `DeterministicFakeEmbedding` | 增量同步对不对？按方向过滤对不对？两个集合会不会互相覆盖？ |
| ④ 假网络的爬虫测试 | 注入假的 `post_json`、`get_text`、`sleep` | **每一条约束**：被 robots 禁止时是否一个请求都没发？遇到 401、403、429 是否只请求了一次、不重试？间隔次数对不对？上限超了是否报错？停止时是否保留了已收集的？ |
| ⑤ 页面交互测试 | Streamlit `AppTest` | 点按钮后有没有结果？失败时是否只显示错误类型？选了“抓取的岗位”后是否出现方向下拉框、按方向过滤是否生效？ |
| ⑥ 真实运行（**手动**） | 真实模型、真实 embedding、真实浏览器、真实站点 | 模型判得准不准？页面好不好看？站点真的会这样返回吗？ |

**测试驱动的节奏**：每个功能先写测试 → 运行 → 看到**红** → 写实现 → **绿**。这个“红”证明测试真的在检查东西。

**几个习惯**：

- 手算好的期望值写进测试，而不是用代码算期望；
- 断言**状态码**，不断言整句中文；
- 院校名单、联网和睡眠都作为**参数**传入，测试不依赖本机文件和网络；
- **失败路径比成功路径更重要**：爬虫测试里“被拦下以后没有再多发一个请求”“抓到一半被拦也保存已有的”“拒绝的批次什么都不写”；
- 专门写了“失败时不泄露 key”和“绝不保存联系人”的测试：让假数据里带上联系人姓名和内部 ID，断言输出里没有；
- **上午只验证了最终状态，下午改成逐个提交验证**（`git worktree`）。

## 9. 设计合理性的评价

| 决策 | 合理在哪 | 代价 / 风险 |
|---|---|---|
| **模型判断，代码算分** | 分数确定、可复现、可追溯到具体技能 | 分数只反映“满足了几项”，不反映“满足得多深”；所有技能权重相等 |
| **岗位技能清单以 JD 为准，用代码对齐** | 分母不受模型波动影响；漏判时保守处理 | 依赖岗位抽取的质量 |
| **缓存岗位抽取** | 同一份 JD 结果固定；省时间省钱 | 改提示词后缓存自动作废，包括手工修正过的内容 |
| **容错版依据核对** | 严格逐字核对会误伤约一半正确判断 | 拦不住“引用真实但推理不对”；纯中文改写仍可能被误判 |
| **向量检索只做粗筛，最终按总分排序** | 检索只说明“话题相近”，实测算法岗检索距离最远却得分最高 | 挑不进来的岗位不会被评分，**k 太小会漏掉更合适的岗位**；查询文本会把检索带偏 |
| **岗位按内容哈希增量同步** | 只给新增岗位算 embedding | 两个文件内容完全相同会被当成一个 |
| **学历和学校单独展示，不计入总分** | 名称匹配会出错，自动据此拉低分数会误伤 | “985/211优先”本质是偏好，却显示“不满足”，措辞偏重 |
| **依赖注入 + 假模型/假网络** | 278 个测试全部离线，不花钱 | 假的证明不了“模型判得准”或“网站真的这样返回” |
| **爬虫的约束写进代码并测试** | 约束不会被遗忘或绕过；失败路径有测试 | 约束是我们自己定的“礼貌”标准，**不能代替阅读网站的用户协议**，而协议我没找到 |
| **不绕过验证码和 `robots.txt`** | 合规；避免个人信息和条款风险 | 拿不到 BOSS 直聘这类平台的数据 |
| **名额平均分配给每个关键词** | 每个专业方向都有数据 | 关键词多了每个关键词的名额就少；总量是硬上限 |
| **自己定专业方向，不用站点的“专业要求”** | 可控，且不受 117 条“不限”的影响 | 方向是按**搜索关键词**归类的：用“数据分析”搜出来的岗位被归为“数据”方向，岗位本身可能其实属于别的方向 |
| **抓取岗位用独立的向量集合** | 同步一个不会删另一个的岗位 | 两个集合要分别维护 |
| **调用网站内部接口而不是解析页面** | 请求量少（列表接口已含全文）；数据结构化 | 不是公开 API，网站改版会失效；比“浏览网页”更进一步，更依赖使用者对协议的把握 |
| **单文件 `jobs.jsonl`** | 一个文件好管理、可只追加、坏一行不影响其他 | 不是数据库，量大了要换 |

## 10. 还没解决的问题

按重要性排序：

1. **没有标注测试集**：所有“模型判得准不准”和“检索是否合理”的说法，都只建立在 1 份简历上。这是和成熟项目差距最大的地方。
2. **检索和评分不一致、查询文本把检索带偏**（难题 19）：没做改进，也没做对照实验确认原因。
3. **国聘的用户协议没有核对**：我没找到原文，无法判断“个人学习用途的小规模抓取”是否被允许。使用者必须自己确认；接口是网站的内部接口，改版会失效。
4. **抓取的数据有明显的来源偏差**：偏校招、偏央企国企，一个平台的切片；117 条没有写具体专业；分数整体偏低（样例简历很薄，而校招岗位常要求硕士、技能清单很长），最高也只有十几到三十几分。
5. **校名是精确匹配**：简历写“中国地质大学（武汉）”、“北邮”会被判为“未收录”；教育部名单是 2005、2006 年的版本，改过名的学校会匹配不上。
6. **院校只有 985/211 两个层次**：分不清“确实不是 985/211”和“名单里没有这个名字”。
7. **没有做偏见测试**：模型判断时看的是整份简历原文，含姓名、性别、学校信息；研究里有“换姓名或性别后分数是否稳定”的反事实测试，这个项目还没做。
8. **模型给的依据有时很笼统**（比如整行技能清单当依据），依据核对只检查“出自原文”，不检查“贴不贴切”。
9. **网页新增的“岗位来源”和“专业方向”选项没有在真实浏览器里看过**，只用 `AppTest` 测了交互逻辑；样例简历也没有“专业”字段，所以不能自动推断该选哪个方向。
10. **推送**：远程仓库已配置，推送由使用者在自己的终端完成（登录凭据我不处理），**我没有核对过推送结果**。
11. **`requirements.txt` 没有锁版本**。
12. “A 或 B”被拆成两项都必备，对这类岗位偏严；软素质完全不参与评分。

## 11. 这一天学到的东西

1. **让模型做它擅长的（理解、判断），让代码做它擅长的（计算、对齐、校验、约束）**。这是整个项目最重要的设计原则。
2. **对不确定的东西先实测**：新模型的输出是否干净、严格核对会不会误伤、网站的接口长什么样，都是先看数据再决定设计。
3. **测试驱动要看到“红”**：红证明测试有效。
4. **依赖注入让大模型应用和爬虫都可测试**：把 `llm`、`embedding`、缓存、网络、睡眠都作为参数传入。
5. **单元测试全绿 ≠ 没有 bug**：985/211 的 bug、依据被截断、总分在手机上看不到、依据被改写后误判，都是真实运行才暴露的。**真实数据和单元测试要两者都做。**
6. **数字要核对，别凭印象**：数量校验（39/112）帮我们发现数据对不对；我自己也说错过测试数和提交数，被实测数据纠正。
7. **合规是设计的一部分**：先读 `robots.txt`，规则堵住的就不做；验证码和登录不绕；个人信息不存；数据不提交；**自己定的限制要写进代码并测试**。同时要清楚地知道“礼貌”不等于“被允许”。
8. **规模变化要重新确认**：总量从 100 提到 300 时，我没有擅自改，而是先请使用者确认。
9. **失败路径比成功路径更值得测试**：被拦下之后“不再多发一个请求”“保留已经收集的”，比“正常抓到数据”更能体现可靠性。
10. **“能抓到”不等于“数据好”**：297 条里 213 条是校招，一个平台的切片。拿到数据后要先看分布，别只看数量。
11. **每次提交都应该能独立通过**：分次提交时依赖关系会暴露出来，用 `git worktree` 逐个验证才能放心。
12. **诚实地写局限**：README 的“已知局限”和本文第 8.4、第 10 节，比一份漂亮的功能清单更有价值。

**面试里可以这样讲这个项目**：

> 两阶段岗位推荐：向量检索（Chroma + bge-m3，按专业方向做元数据过滤）粗筛候选岗位，大模型逐项判断技能是否满足并给出依据，最终分数由代码按权重计算，所以每个分数都能追溯到具体技能。可靠性方面做了岗位技能清单对齐、依据核对、岗位抽取缓存。数据方面，在先查 `robots.txt`、限速限量、遇阻即停、不存个人信息的约束下，从国聘小规模抓取了覆盖 9 个专业方向的 297 条岗位，这些约束都有测试。278 个测试全部离线，通过依赖注入和假模型、假网络实现。局限是评估样本还很小，没有标注测试集，抓取的数据偏校招和国企。
